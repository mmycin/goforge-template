# GoForge Template — Agent Workspace

> **Project**: [GoForge](https://github.com/mmycin/GoForge) — a production-ready Go framework and CLI.
> This repository is the **generated application template**, not the CLI product itself.
> **Go version**: 1.25.0 | **Module**: `github.com/mmycin/GoForge`

---

## Project Overview

GoForge is a Go microservice framework with built-in HTTP/gRPC servers, database migrations (Atlas), SQL code generation (sqlc), request validation, structured logging, and a Limen-based authentication system. The template scaffolds a complete project with a clear separation between framework-owned code and user-owned code.

**Entry point**: `app/main.go` → `console.Execute()` → reads `.env` and dispatches commands.

## Non-Negotiable Rules

1. **No package-level mutable state** in `internal/` or `core/`.
2. **Constructor-based dependency injection** — prefer `New*` functions.
3. **Imports must use** `github.com/mmycin/GoForge/boot/...` or `github.com/mmycin/GoForge/core/...`.
4. **Never edit** `boot/` or `core/` — if logic belongs there, it belongs in `internal/services/`.
5. **Keep transport thin** — business logic lives in services, not handlers.
6. **Always validate at the handler edge** using `core/validator`.
7. **Never write raw `c.JSON(...)` for errors** — use `c.Error(appErr)`.
8. **Keep route registration local** to the owning service package.
9. **Run `goforge migrate` after any model change** — schema drift causes runtime errors.
10. **`internal/services/kernel.go` is auto-regenerated** by `goforge gen:service` / `goforge rem:service` — any manual additions must be re-applied after regeneration.

## CLI Commands

```bash
# Project lifecycle
# Run outside any project directory
goforge new [project-name] [module-path]  # Both args required, or interactive wizard
goforge gen:key                          # Generate a secure APP_KEY
goforge rem:key                          # Remove the current APP_KEY

# Service scaffolding
goforge gen:service <name>               # Generate a full service (handler, routes, model, docs, grpc, proto)
goforge rem:service <name>               # Remove a service and its proto files
goforge gen:command <name>               # Generate a custom console command
goforge rem:command <name>               # Remove a custom console command
goforge gen:event <service>              # Add event structs & listeners to a service

# Database
goforge gen:migration <name>             # Generate an Atlas schema migration
goforge migrate                           # Apply pending migrations
goforge rem:migration                    # Remove the latest migration and revert Atlas hash
goforge loader                           # Dump GORM schema as SQL

# gRPC / Proto
goforge gen:proto [service]              # Compile .proto files (picker if no arg)
goforge rem:proto                        # Remove all generated .pb.go files
goforge rem:grpc                         # Surgically remove all gRPC infrastructure (12 steps)

# SQLC
goforge gen:sqlc                         # Generate type-safe Go from queries
goforge rem:sqlc                         # Remove generated SQLC code

# Config
goforge gen:config <name>                # Add a new config section and wire it in

# Running
goforge app serve                        # Start HTTP + gRPC servers
goforge version                          # Show version and build info
goforge readme                           # Show the recommended workflow guide
```

**Shell wrapper**: `./goforge.sh <cmd>` proxies to `go run app/main.go` — equivalent to `goforge app <cmd>`.

All commands use an interactive TUI (Catppuccin theme). When a name is omitted, a form is shown. Long-running operations show a progress screen. Destructive commands (`rem:*`) show a confirmation dialog first.

## Agent Commands

All agent commands live in `.agent/commands/`. Use them by referencing the command name.

| Command | Purpose |
|---------|--------|
| **context** | Read at the start of any session. Establishes project facts and non-negotiables. |
| **next** | Choose the next safe step. Decision order for locating the owning package. |
| **review** | Code review / pre-merge checks. Prioritizes bugs, regressions, security, tests. |
| **ship-feature** | End-to-end feature delivery workflow. |
| **state** | Map the current system before changing it. Captures wiring, dependencies, config keys. |
| **session-end** | Close out work cleanly. Checklist for changes, tests, migrations, and risks. |

### Command Details

**`context`** — Read in this order:
1. `README.md`
2. `.agent/rules/architecture.md`
3. `.agent/rules/testing.md`
4. The service or package you will touch

**`next`** — Decision order:
1. Identify the user-visible outcome
2. Locate the owning package
3. Prefer editing existing files over creating new ones
4. If service change → inspect `internal/services/<name>/`, `kernel.go`, `internal/database/`, `internal/proto/<name>/`
5. If startup/transport change → inspect `boot/kernel.go`, `boot/server/http.go`, `boot/server/grpc.go`
6. If config/errors/validation change → inspect `core/config/`, `core/errors/`, `core/validator/`

**`review`** — Priority order:
1. Bugs → 2. Regressions → 3. Security/config risks → 4. Missing tests → 5. Minor maintainability

**`ship-feature`** — Workflow:
1. Read `.agent/commands/context.md`
2. Identify which skill applies under `.agent/skills/`
3. Implement smallest coherent change first
4. Update wiring, config, migrations, tests in same pass
5. Verify with targeted tests before broad runs

**`state`** — Answer these questions:
1. Where is the behavior wired in?
2. What dependencies are injected?
3. What config or env keys influence it?
4. What tests currently cover it?

**`session-end`** — Checklist:
1. Summarize what changed and why
2. Note files needing follow-up
3. Record tests run and not run
4. Call out config, migration, or deployment implications
5. Mention if change needs a matching `goforge-cli` template update

## Agent Rules

All rules live in `.agent/rules/`. These are binding constraints.

### Architecture (`.agent/rules/architecture.md`)
- `boot/` — framework bootstrap, never edit
- `core/` — framework packages, never edit (config, database, errors, validator, console)
- `internal/` — user-owned, everything editable
- No package-level mutable state; prefer constructor injection
- Keep framework bootstrap concerns in `boot/` and `core/`
- If a change belongs in the generator, stop and confirm whether `goforge-cli` should be updated
- Imports must use `github.com/mmycin/GoForge/boot/...` or `github.com/mmycin/GoForge/core/...`

### API Design (`.agent/rules/api-design.md`)
- Keep transport thin; business logic in services
- Validate at handler edge using `core/validator`
- Return consistent errors via `c.Error()` — never `c.JSON` for errors
- `ErrorHandler` middleware writes all error responses
- Keep route registration local to owning service
- gRPC: maintain graceful shutdown, avoid long-running uncontrolled goroutines
- Prefer additive API changes

### Database (`.agent/rules/database.md`)
- Update models deliberately
- Consider migration impact immediately
- Keep DB access behind service methods or query layers
- Use `GetGorm()` safely and handle errors
- Do not hide schema changes inside unrelated refactors
- Keep SQLC generated code in sync with query changes

### Testing (`.agent/rules/testing.md`)
- Run targeted tests for touched packages first
- Run broader tests when startup, transport, or shared wiring changes
- Prefer tests that exercise public behavior, not internals
- Mention unrun tests explicitly
- Missing tests are a real finding, not a footnote

## Agent Skills

All skills live in `.agent/skills/`. Each skill has a `SKILL.md` and may include shell scripts.

### 1. `cli-commands` — GoForge CLI Operations
**SKILL.md**: Full guide to all `goforge` CLI commands, project lifecycle, service scaffolding, database, gRPC/proto, SQLC, config, events, and the typical new-feature workflow.

**Scripts**:
- `new-service.sh <name>` — Scaffold a service, generate migration, and apply it in one step
- `remove-service.sh <name>` — Remove a service and roll back its last migration

### 2. `configuration` — Adding/Renaming/Validating Settings
**SKILL.md**: Add config shape in `core/config/`, load via viper, update `.env.example`, check all call sites. `core/config/` is framework-owned.

### 3. `database-migrations` — Schema Changes
**SKILL.md**: Change model → run `migrate.sh` → update sqlc queries → run `sqlc.sh` → rollback with `rollback.sh`. `core/database/database.go` is framework-owned.

**Scripts**:
- `migrate.sh <name>` — Generate and apply an Atlas migration
- `rollback.sh` — Remove the latest migration and revert the Atlas hash
- `sqlc.sh` — Regenerate SQLC type-safe query code

### 4. `error-handling` — Error Responses and Status Codes
**SKILL.md**: All errors use `*apperrors.AppError`. Constructor helpers: `ErrBadRequest(400)`, `ErrUnauthorized(401)`, `ErrForbidden(403)`, `ErrNotFound(404)`, `ErrConflict(409)`, `ErrUnprocessable(422)`, `ErrInternalServer(500)`. Wrap original errors for logging. Never write raw `c.JSON` for errors.

### 5. `goforge-core` — Bootstrap and Shared Wiring
**SKILL.md**: For tasks touching `boot/kernel.go`, `internal/services/kernel.go`, `app/main.go`. Covers app construction, dependency injection, service registration, startup/shutdown. Keep bootstrap in `boot/` and `core/`.

### 6. `http-grpc` — Transports, Middleware, Routing
**SKILL.md**: Read `boot/server/http.go`, `boot/server/grpc.go`, `boot/server/middleware/`, and the owning service's handler/routes/grpc files. Proto files in `internal/proto/<name>/<name>.proto`, generated code in `internal/proto/<name>/gen/`.

**Scripts**:
- `proto.sh [name|--clean]` — Compile proto definitions or remove generated `.pb.go` files

### 7. `limen-auth` — Authentication (Registration, Login, Sessions)
**SKILL.md**: Full guide for Limen auth. Uses `github.com/thecodearcher/limen` with `credential-password` plugin and `limengorm` adapter. Provides `/register`, `/login`, `/logout`, `/me` endpoints.

**File layout** (`internal/services/auth/`):
- `model.go` — User, Session, Verification, Account structs
- `service.go` — `limen.New(...)` + `var Auth`
- `routes.go` — Mount `gin.WrapH(Auth.Handler())` at `/api/auth/*action`
- Delete `handler.go`, `grpc.go`, `docs.go`, `internal/proto/auth/`

**Scripts**:
- `install-deps.sh` — Install Limen core, gorm adapter, credential-password plugin
- `migrate.sh` — Generate and apply Limen schema migration
- `scaffold.sh` — Scaffold auth service, remove incompatible files, install deps
- `test-endpoints.sh [base-url]` — Smoke-test auth endpoints with curl

### 8. `testing` — Test Execution
**SKILL.md**: Test map: `internal/tests/http/`, `internal/tests/grpc/`, `internal/tests/integration/`, `internal/tests/unit/`. Run narrowest tests first, expand if shared code changed.

**Scripts**:
- `run.sh [scope]` — Run tests: `http`, `grpc`, `integration`, `unit`, or `all` (default)

### 9. `tls` — TLS/HTTPS Configuration
**SKILL.md**: Configure `TLS_ENABLED`, `TLS_CERT_FILE`, `TLS_KEY_FILE` in `.env`. Read `core/config/http.go` and `boot/server/http.go`. For local dev, generate self-signed certs. For production, use a CA or `acme/autocert`.

**Scripts**:
- `gen-cert.sh [days] [CN]` — Generate self-signed TLS certificate (defaults: 365 days, CN=localhost)

### 10. `validation` — Request Validation
**SKILL.md**: `core/validator` wraps `go-playground/validator/v10`. Annotate structs with `validate:` tags. Call `validator.Validate(req)` after `ShouldBindJSON`. Returns `*apperrors.AppError` (422) with per-field details. Supports custom rules via `validator.RegisterRule`.

## Build & Deployment

**Docker**: Multi-stage build. Stage 1 (`golang:1.24-alpine`) builds the binary with all tools. Stage 2 (`alpine:3.21`) runs as non-privileged `appuser` on port 3000.

**Live reload**: `air` configured via `air.toml` — builds `./app` to `tmp/main`, watches `.go`, `.tpl`, `.tmpl`, `.html` files.

**Default port**: 3000 (configurable via `.env`).

**Production**: See `goforge-docs/docs/deployment/` for security checklist, systemd, Kubernetes, and zero-downtime deployment guides.

**Graceful shutdown**: `SIGINT`/`SIGTERM` triggers 10-second drain for all servers, then 30-second event bus drain.

## Quick Reference: Common Workflows

### Adding a new service
```bash
bash .agent/skills/cli-commands/new-service.sh <name>
# Edit internal/services/<name>/{model,service,handler,routes,events,listeners}.go
# (Optional) goforge gen:event <name>
# (Optional) goforge gen:proto <name>
# (Optional) goforge gen:sqlc
goforge app serve
```

### Adding auth
```bash
bash .agent/skills/limen-auth/scaffold.sh
# Rewrite model.go, service.go, routes.go
# Update kernel.go (register 4 models + auth.Initialize())
bash .agent/skills/limen-auth/migrate.sh
goforge app serve
```

### Adding a database field
```bash
# Edit internal/services/<name>/model.go
bash .agent/skills/database-migrations/migrate.sh <name>
# If using sqlc, edit queries and run:
bash .agent/skills/database-migrations/sqlc.sh
```

### Adding events to a service
```bash
goforge gen:event <name>
# Edit events.go and listeners.go with real logic
# Register listeners in internal/services/kernel.go
goforge app serve
```

### Adding a config section
```bash
goforge gen:config <name>
# Add env vars to .env
# Use config.<Name> in your services
```

### Running tests
```bash
bash .agent/skills/testing/run.sh          # all scopes
bash .agent/skills/testing/run.sh http     # HTTP only
bash .agent/skills/testing/run.sh unit     # Unit only
```

### Enabling TLS
```bash
bash .agent/skills/tls/gen-cert.sh
# Set TLS_ENABLED=true, TLS_CERT_FILE=cert.pem, TLS_KEY_FILE=key.pem in .env
```

### Removing gRPC
```bash
goforge rem:grpc
# Surgically removes all gRPC infrastructure in 12 steps
# Leaves a pure REST codebase
```

### Code review checklist
- Behavior regressions first, style second
- Broken DI or accidental globals
- Missing updates in `internal/services/kernel.go`
- Config keys missing from `.env.example`
- gRPC shutdown and timeout handling
- Middleware or route registration drift
- Database model changes without migration impact
- Tests missing for new behavior
- Edits made to `core/` or `boot/` that should live in `internal/services/`
- Module path consistency (`github.com/mmycin/GoForge`)
